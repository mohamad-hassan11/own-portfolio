## Overview

During my Software Engineering graduation project at DEVENTit, I investigated how to add natural-language search to Atlantis, an enterprise collection management platform. The goal was to help users find collection records through conversational questions while preserving the platform’s existing authentication and authorization rules.

I combined analysis of an unfamiliar enterprise security model with technology research, architecture design, iterative prototyping, and scenario-based evaluation. The delivered work comprised a graduation research report, requirements and architecture documentation, and a working proof of concept for indexing and retrieving collection data.

The central decision was to keep Atlantis responsible for access control. The retrieval service proposes relevant document identifiers; Atlantis checks those candidates against the authenticated user’s rights before returning results to the interface.

## The problem and its constraints

Atlantis supports complex collection descriptions, structured filters, and configurable workflows. Using that functionality effectively requires knowledge of the interface and the underlying collection structure. A natural-language assistant offered another way to search, but it also introduced a new route through which restricted information could become visible.

Access depends on several interacting mechanisms: user-group rights, segment restrictions, record security levels, and backend checks. Interface permissions also affect which controls a user sees, but visibility of a button is not an authorization boundary. The integration had to preserve those distinctions rather than reproduce a simplified version of the rights model inside an LLM prompt.

I scoped the proof of concept to search and retrieval. Report generation, moderation, record linking, and other write operations remained possible future extensions rather than delivered functionality.

## My role and research approach

I carried out the graduation research and prototype development, consulting Atlantis developers and support specialists to clarify domain behavior and integration constraints. My work covered the security analysis, product requirements, technology comparison, C4 and runtime diagrams, retrieval-service implementation, indexing design, and evaluation.

The research followed four phases: understand Atlantis and its security boundaries; compare LLM and retrieval technologies; translate the findings into prototypes; and evaluate indexing, retrieval, and authorization behavior. Weekly progress discussions and experiments helped turn open questions into concrete design decisions.

One useful clarification came from discussing default segments and security levels with domain specialists. A user’s default segment determines the initial assignment of newly created records; it does not define that user’s access. Group memberships and their restrictions determine access. Resolving that distinction prevented a misleading interpretation from entering the integration design.

## Technology decisions

I compared managed LLM APIs with open-weight models deployed in the cloud or on premises. For this proof of concept, managed providers offered a practical route to tool invocation and structured output without requiring a separate GPU infrastructure project. Self-hosting remained a future option when data custody, predictable utilization, or operational requirements justify it.

The service separates model providers, embeddings, retrieval storage, and orchestration. This keeps experimentation outside Atlantis business logic and makes the integration depend on a service contract rather than a particular model.

The experiments used different storage approaches. Chroma introduced semantic retrieval; a subsequent Qdrant prototype explored dense and sparse hybrid search. The delivered Python service in the final project folder uses Elasticsearch, combining BM25 lexical retrieval with dense-vector search and Reciprocal Rank Fusion. Those experiments are stages of the project, not a single production stack.

## From API translation to hybrid retrieval

**Prototype A — Translate intent into an existing API request.** A code-based agent produced a structured search request and called the Atlantis search API with the user’s access token. This demonstrated integration with existing authorization, but forwarding complete search responses to the model exposed more data than was needed for interpreting intent.

**Prototype B — Test visual orchestration.** I recreated the approach in n8n to explore workflow-based integration. It demonstrated feasibility while raising questions about version control, testability, and maintaining complex orchestration in an enterprise codebase.

**Prototype C — Make the workflow more explicit.** Chained LLM steps separated request construction from filter extraction, with deterministic code applying filters before the API call. This reduced dependence on open-ended agent behavior.

**Prototype D — Add an independent retrieval index.** A code-based service introduced batch indexing, Chroma embeddings, semantic search, and structured filters. Retrieved candidate identifiers were checked through Atlantis before presentation.

**Prototype E — Combine meaning and exact terms.** The Qdrant experiment added lexical retrieval alongside dense embeddings. The final service implements the hybrid approach with Elasticsearch and an additional model-assisted relevance-ranking stage.

## Architecture and the authorization boundary

The user interacts with Atlantis. Its backend coordinates the query, calls a separate Python RAG service, and applies existing rights checks to candidate document identifiers. The RAG service owns retrieval concerns: prompt interpretation, metadata filters, embeddings, search, and ranking.

I compared two places to enforce rights after retrieval. Filtering in the frontend would allow unauthorized candidate identifiers to reach the browser before removal. Filtering in the Atlantis backend keeps that decision inside the trusted application boundary. I selected backend enforcement through the existing search infrastructure using the caller’s access token.

This distinction applies even when the response contains only identifiers. An identifier can still reveal that a restricted record exists. The result contract therefore returns authorized identifiers to the interface, which uses the existing Atlantis search-results experience.

This boundary governs what reaches the end user. It does not by itself establish which retrieved content can safely be sent to an external model; provider data handling and minimizing model context remain separate concerns.

## Preparing collection data for retrieval

The indexing flow retrieves Atlantis records in pages, maps them into a retrieval-oriented document format, and sends manageable batches to the RAG service. The service prepares searchable content and filterable metadata, generates embeddings in batches, and bulk-indexes the resulting documents.

The implementation builds distinct lexical and semantic representations. Lexical content preserves searchable identifiers and metadata terms; semantic content assembles descriptive text with contextual fields. Moderation state, document type, multimedia presence, and multimedia counts are represented separately for filtering.

The report documents a background indexing job that returns a job identifier, indexing from a selected page, and an Elasticsearch collection containing 19,691 documents. This is evidence of a working batch pipeline on a partial demonstration collection, rather than a throughput benchmark or proof of full-environment coverage.

During development, malformed test-environment records interrupted indexing because digital files lacked their expected versions. I investigated the failure with a colleague; the team resolved the invalid source data through its synchronization process. The experience showed why validating domain assumptions and involving platform specialists matter as much as the embedding code.

## How a search moves through the system

**Interpret the question.** The model extracts the topic and supported metadata constraints into structured tool arguments. For example, a request for moderated documents about roses separates the topic from the moderation filter.

**Retrieve through two complementary branches.** Elasticsearch runs BM25 over lexical content and nearest-neighbor search over dense embeddings. Supported metadata constraints are applied to both branches so they search the same eligible content.

**Fuse and assess relevance.** Reciprocal Rank Fusion combines the ranked lists. The prototype then uses a model-assisted ranking stage to remove empty, duplicate, or unrelated candidates and order the remaining identifiers by relevance.

**Enforce rights and present results.** Atlantis checks the candidates using its existing authorization-aware search. The interface then presents the permitted records through the existing results flow.

The FastAPI service exposes Server-Sent Events for progress updates. The assistant panel makes stages such as query interpretation, retrieval, and ranking inspectable during the proof of concept. These are application progress and tool events, rather than a guarantee that model reasoning is correct.

## Evaluation and observed results

**Indexing.** The research documents record export, transformation, embedding enrichment, bulk storage, and background batch execution. The indexed collection demonstrates that the flow worked beyond isolated sample records.

**Retrieval.** Scenario tests show natural-language prompts becoming search terms and structured filters, followed by results displayed in Atlantis. English prompts about war and a mayor also returned relevant collection results, providing examples of cross-language retrieval behavior.

**Authorization.** The evaluation compares a record appearing for a user with sufficient rights and being absent for a user without those rights. This supports the intended separation between retrieval relevance and permission to view a record.

The evaluation establishes proof-of-concept feasibility. It does not establish a measured relevance improvement, comprehensive tenant-isolation assurance, production latency, or resistance to every adversarial prompt. The reported tests are scenario-based, not an exhaustive security audit or a controlled retrieval benchmark.

## Limitations and next steps

Retrieval quality depended heavily on preprocessing and source metadata. Incomplete or inconsistent descriptions weakened filtering and produced ambiguous, duplicate, or poorly matched results. Better field selection and normalization would be a priority before changing models.

The indexed image-document collection represented only part of the demonstration environment. Coverage across other document types and collections remained unverified. Free-tier model and token limits also constrained result sizes and the scope of experimentation.

A next phase would define a repeatable set of labeled queries, measure top-k relevance and filter extraction accuracy, broaden authorization tests, and evaluate the workflow with actual users. Production work would also need explicit review of provider data exposure, operational resilience, and resource limits. Any write-capable tools would require their own validated execution and authorization design.

## What I learned

I began with no prior practical experience of LLM tooling. Building the prototypes required learning embeddings, hybrid search, orchestration, and architecture notation while working within an established enterprise application.

The most valuable lesson was to investigate retrieval quality and domain assumptions before adding agent complexity. Better document representations, explicit tool inputs, and a clear authorization boundary made the design easier to explain and assess. Consulting domain experts early also helped resolve uncertainties that source code and documentation alone did not answer.

The project demonstrated my ability to research an unfamiliar technical area, make and document tradeoffs, build an integrated prototype, and distinguish a promising result from evidence of production readiness.
